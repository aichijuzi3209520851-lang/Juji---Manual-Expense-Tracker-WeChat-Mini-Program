[P][Heading 1] 第 2 章 数据库选型与环境
[P][Heading 2] 2.1 选型决策
[P][Normal] 橘记选择 CloudBase 文档型 NoSQL 而非关系型数据库，基于以下对比分析：
[P][Normal] 表 2-1：数据库选型对比
[TABLE 4]
对比维度 | 文档型 NoSQL | 关系型数据库 | 橘记适配性
Schema 灵活性 | 动态 Schema，字段可随时增减 | 固定 Schema，变更需 ALTER TABLE | NoSQL 更适合快速迭代
微信生态集成 | 原生集成，_openid 自动注入 | 需额外开发登录对接 | NoSQL 集成成本为零
运维成本 | Serverless，免运维 | 需管理服务器、备份、扩容 | NoSQL 适合个人开发者
查询复杂度 | 支持基础聚合，无 JOIN | 复杂 JOIN、事务 | 橘记无跨表 JOIN 需求
[/TABLE]
[P][Normal] 选择 CloudBase 文档型 NoSQL 的四条核心理由：
[P][List Bullet] 无需自建和运维数据库服务器，按量计费
[P][List Bullet] 与微信小程序云开发原生集成，_openid 自动注入
[P][List Bullet] 文档结构适合账单、用户偏好等半结构化数据的快速迭代
[P][List Bullet] Serverless 按量计费，适合个人开发者与竞赛项目

[P][Heading 2] 2.3 数据隔离机制
[P][Normal] 橘记通过三层机制确保用户数据完全隔离：
[P][List Bullet] 第一层（数据库层）：数据库安全规则：所有 5 个集合配置为"仅创建者可读写"，CloudBase 在数据库层强制过滤，每个用户只能查询和修改 _openid 等于自身 openid 的文档
[P][List Bullet] 第二层（服务端）：云函数 OPENID 服务端获取：写操作在云函数中通过 cloud.getWXContext().OPENID 获取身份，不信任客户端传入的 openid
[P][List Bullet] 第三层（代码层）：写操作显式所有权校验：bills.delete/update 操作在执行前查询文档 _openid 并与服务端 openid 比对，不匹配则拒绝

[P][Heading 2] 3.2 实体关系说明
[P][Normal] 5 个集合之间的逻辑关系：所有集合以 _openid 作为逻辑外键关联到用户。bills 与 users 通过 _openid 和 users.customCategories 产生间接关系（分类名须在用户分类列表中存在）。budgets 与 bills 在业务层面共同服务于预算进度计算，但数据库层无直接关联字段。ai_usage_limits 和 client_logs 均为 users 的附属功能集合。
[P][Heading 2] 3.3 设计模式说明
[P][Normal] 橘记采用三种 NoSQL 设计模式：
[P][List Bullet] 内嵌文档（Embedded Document）：users.customCategories 内嵌分类数组，避免跨集合查询。数量级小（数十条以内），与用户档案一同读取
[P][List Bullet] 基于 ID 构造的幂等计数器：ai_usage_limits 用 openid_date_feature 作为 _id，实现按日按功能的幂等限流计数器
[P][List Bullet] 一对一月份归档：budgets 一月一条，用 month 字段定位，通过 upsert 防重复，原子性保证

[P][Heading 1] 第 5 章 budgets 集合详细设计
[P][Normal] budgets 集合存储用户每月预算金额。设计决策为"一月一条 upsert"——每月仅保存一条最新预算文档，通过 upsert 操作避免历史记录膨胀，同时保留月度历史（近 6 条）用于达成率图表。

[P][Heading 2] 5.2 Upsert 操作逻辑
[P][Normal] budgets 云函数的 upsert 流程：
[P][List Bullet] 构造查询条件：{ _openid: OPENID, month: "YYYY-MM" }
[P][List Bullet] 执行 upsert：若文档存在则更新 amount + updatedAt；若不存在则插入新文档（含 createdAt）
[P][List Bullet] 选择 upsert 而非先 delete 再 insert 的原因：原子性保证，避免并发竞态导致数据丢失

[P][Heading 2] 6.2 内嵌 vs 引用设计决策
[P][Normal] 将 customCategories 和 user_themes 内嵌在 users 文档而非独立集合的理由：
[P][List Bullet] 数量级小：分类最多数十条，主题最多 5 条，内嵌不影响文档大小
[P][List Bullet] 与用户档案一同读取：profile 页一次查询获取全部信息，无需联查
[P][List Bullet] CloudBase NoSQL 不支持 JOIN，内嵌是正确的 NoSQL 设计模式

[P][Heading 1] 第 7 章 ai_usage_limits 集合详细设计
[P][Normal] ai_usage_limits 是一个计数器集合，核心设计亮点是用文档 _id 的拼接格式（openid_date_feature）实现幂等限流计数器，每用户每功能每天最多 2 条文档（profileLetter + profileTitle），数据量级极低。
[P][Heading 2] 7.1 _id 拼接设计详解
[P][Normal] _id = `${openid}_${date}_${feature}` 的设计意图：
[P][List Bullet] 唯一性：同一用户同一天同一功能的限流文档 _id 唯一，天然避免重复创建
[P][List Bullet] 幂等 upsert：aiPoster 云函数直接用 _id 定位文档，有则读取 count，无则 upsert 初始化，无需先 findOne 再决定 insert/update
[P][List Bullet] 自动过期：旧日期文档可通过定期清理删除，_id 中编码了日期信息便于识别
[P][Normal] 对比方案：若用普通自动 _id + 查询 openid+date+feature 三字段，会多一次查询且存在并发竞态。_id 拼接方案在数据库层面就保证了唯一性。

[P][Heading 2] 8.2 上报机制
[P][Normal] monitor.js 通过 initMonitoring()（幂等，_inited 标志防重复注册）在 app.js onLaunch 中调用一次，注册 wx.onError（捕获运行时 JS 错误）和 wx.onUnhandledRejection（捕获未处理 Promise 拒绝）全局钩子。上报为"尽力而为"——上报失败不影响主流程。
[P][Heading 2] 8.3 数据清理策略
[P][Normal] CloudBase 文档数据库不支持 TTL 索引（与 MongoDB 不同），client_logs 需手动清理。建议运维策略：
[P][List Bullet] 每月在 CloudBase 控制台按 createdAt < 30 天前条件批量删除
[P][List Bullet] 大版本发布后检查是否有高频异常
[P][List Bullet] ai_usage_limits 旧日期文档也可定期清理（date < 30 天前）

[P][Heading 2] 9.3 写操作权限校验流程
[P][Normal] 以 bills.delete 为例的三步校验：
[P][List Bullet] cloud.getWXContext().OPENID 获取服务端 openid（不可伪造）
[P][List Bullet] db.collection("bills").doc(billId).get() 查询文档
[P][List Bullet] 校验文档._openid === 服务端 openid，不一致则返回"无权操作"并终止
[P][Normal] 为何不在数据库规则直接拒绝而要在代码中再做一次校验：提供明确的错误信息，方便日志追踪和用户提示。

[P][List Bullet] 导入：dataMigration 分批写入（每批 20 条），前端清洗内部字段
[P][List Bullet] 一键清除：clearUserData 按 _openid 删除全部 bills/budgets/文件并重置 users（无客户端参数参与，服务端自主作用域）
